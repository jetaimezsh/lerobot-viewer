# LeRobot Viewer v4.0 — 模型回测框架设计文档

## 1. 背景与动机

### 1.1 现状

v3.x 的模型回测系统存在以下问题：

| # | 问题 | 表现 |
|---|------|------|
| 1 | **注册信息不持久化** | `MODEL_REGISTRY` 是进程内存字典，服务重启即丢失，每次都要重新注册 |
| 2 | **参数不可复用** | 同一模型改个参数就得删了重建，且表单字段固定，无法为不同策略配置不同推理参数 |
| 3 | **回测流程繁琐** | 注册 → 检查 → 加载 → 切到回测页 → 选模型 → 运行，中间步骤太多 |
| 4 | **无法接入自定义模型** | `custom_script` 适配器声明了但未实现，所有非 `lerobot_official` 的策略（自训练模型、其他框架）都无法接入 |
| 5 | **缺少统一参数入口** | ACT 的 `n_obs_steps`、DP 的 `horizon` / `num_inference_steps`、用户自己的 `chunk_size` 等参数散落在代码各处，没有一个统一的地方管理和修改 |

### 1.2 目标

构建一个 **可持久化、可配置、可扩展** 的模型档案（Model Profile）系统：

1. **一次配好，反复使用**：所有模型配置持久化到磁盘，Web 上随时加载使用
2. **内置模板 + 自由定制**：提供 ACT / DP / VQ-BeT 等常见策略的参数模板，同时允许用户从头创建或修改任何参数
3. **支持自定义脚本接入**（Phase 2）：通过子进程 JSON 协议，任何语言、任何框架的模型都能接入回测
4. **回测流程简化**：勾选模型 + 样本 → 一键运行

## 2. 核心设计：Model Profile

### 2.1 概念

**Model Profile** = 一个模型的完整"身份档案"，是一个存于磁盘的 `.json` 文件，包含：

- 模型身份（名称、checkpoint 路径、适配器类型、设备）
- 所有推理参数（policy_type、n_obs_steps、chunk_size 等）
- 用户自定义的任意 key-value 扩展

### 2.2 文件布局

```
model_profiles/               ← 项目根目录下的 profile 存储目录
├── act_pusht.json            ← 每个 profile 一个 .json 文件
├── dp_push_t.json
├── vq_bet_kitchen.json
├── my_custom_model.json
└── .templates/               ← 用户另存为模板的 profile（可选）
    └── my_template.json
```

- 文件名 = `{profile_id}.json`，`profile_id` 由用户指定，只允许 `[a-z0-9_-]`，如 `act_pusht`
- 可读、可手改、可 git 版本管理
- `.gitignore` 中默认忽略 `model_profiles/`，避免将含本地路径的 profile 提交到仓库

### 2.3 Profile 数据结构

```jsonc
{
  // ── 基本元数据 ──
  "id": "act_pusht",
  "name": "ACT pusht (n_obs=2)",
  "description": "ACT policy on pusht dataset, trained 100 epochs",

  // ── 运行时配置 ──
  "checkpoint_path": "/data/checkpoints/act_pusht",
  "adapter": "lerobot_official",
  "device": "cuda",

  // ── 推理参数（模板提供默认值，Web 可编辑值但不可删键）──
  "inference_params": {
    "policy_type": "act",
    "n_obs_steps": 2,
    "n_action_steps": 8,
    "chunk_size": 100,
    "temporal_agg": true
  },

  // ── 用户自定义扩展参数（Web 自由增删）──
  "extra_params": {
    "temperature": 1.0,
    "my_custom_flag": true,
    "notes": "使用了自定义的 stats 归一化"
  },

  // ── 时间戳 ──
  "created_at": "2026-06-01 12:00:00",
  "updated_at": "2026-06-01 14:30:00"
}
```

**字段说明：**

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `id` | string | ✓ | 唯一标识，文件名，只允许 `[a-z0-9_-]` |
| `name` | string | ✓ | 显示名称，任意字符 |
| `description` | string | | 自由描述 |
| `checkpoint_path` | string | ✓ | checkpoint 目录或文件的绝对路径 |
| `adapter` | string | ✓ | 适配器名称，决定如何加载和推理 |
| `device` | string | ✓ | PyTorch 设备名，如 `cuda`、`cuda:0`、`cpu` |
| `inference_params` | object | ✓ | 推理参数，每个适配器定义自己的默认键 |
| `extra_params` | object | | 用户自定义的任意键值对 |

**extra_params 值类型约定：** string / number / boolean / null，前端根据值的 JSON 类型自动选择控件（文本框 / 数字输入 / 开关 / 空值）。

## 3. 适配器系统

### 3.1 架构

```
app/
├── adapters/
│   ├── __init__.py           # BacktestAdapter 抽象基类 + 注册表
│   ├── lerobot_official.py   # LeRobot 官方策略适配器
│   ├── custom_script.py      # 子进程 JSON 协议适配器（Phase 2）
│   └── mock.py               # 测试用 mock 适配器
```

### 3.2 BacktestAdapter 基类

```python
class BacktestAdapter(ABC):
    """所有适配器的抽象基类。"""

    adapter_name: str          # 注册时使用的名称

    @abstractmethod
    def load(self, profile: "ModelProfile") -> None: ...
        """加载模型到内存。"""

    @abstractmethod
    def predict(self, observation: dict[str, Any]) -> np.ndarray: ...
        """给定一帧观测，返回预测动作。"""

    @abstractmethod
    def reset_episode(self) -> None: ...
        """重置策略内部状态（如 LSTM 隐藏状态）。"""

    @abstractmethod
    def unload(self) -> None: ...
        """释放模型，释放显存。"""

    @classmethod
    def default_inference_params(cls) -> dict: ...
        """返回该适配器的默认推理参数模板。"""

    @classmethod
    def validate_params(cls, params: dict) -> list[str]: ...
        """校验推理参数，返回错误列表。"""
```

### 3.3 注册机制

每个适配器文件在末尾自注册：

```python
# app/adapters/lerobot_official.py
from app.adapters import register_adapter
register_adapter("lerobot_official", LeRobotOfficialAdapter)
```

回测引擎通过适配器名称查找适配器类，实例化后加载模型、执行推理：

```python
adapter_cls = ADAPTER_REGISTRY[profile.adapter]
adapter = adapter_cls()
adapter.load(profile)
```

### 3.4 适配器列表

| 适配器名称 | Phase | 说明 |
|-----------|-------|------|
| `lerobot_official` | Phase 1 | 现有 `LeRobotOfficialAdapter` 从 `backtesting.py` 迁出，行为完全不变 |
| `custom_script` | Phase 2 | 子进程 JSON 协议适配器（详见 §8） |
| `mock` | Phase 1 | 测试用，返回随机动作，验证回测流程 |

## 4. 模板系统

### 4.1 目的

用户创建新 profile 时，不需要从零填写所有参数。选择一个模板后自动填充默认的 `inference_params`，在此基础上按需修改。

### 4.2 内置模板

```python
# app/model_templates.py

BUILTIN_TEMPLATES = {
    "act": {
        "label": "ACT (Action Chunking Transformer)",
        "adapter": "lerobot_official",
        "inference_params": {
            "n_obs_steps": 2,
            "n_action_steps": 8,
            "chunk_size": 100,
            "temporal_agg": True,
            "policy_type": "act",
        },
        "description": "适合 pusht、aloha_sim 等单任务。Temporal ensemble 平滑动作预测。",
    },
    "diffusion": {
        "label": "Diffusion Policy",
        "adapter": "lerobot_official",
        "inference_params": {
            "n_obs_steps": 2,

            "num_inference_steps": 100,
            "chunk_size": 100,
            "temporal_agg": True,
            "policy_type": "diffusion",
        },
        "description": "适合同步多模态数据，预测更平滑。horizon 与 n_action_steps 通常相等。",
    },
    "vq_bet": {
        "label": "VQ-BeT",
        "adapter": "lerobot_official",
```

### 4.3 用户自定义模板

- API `POST /api/profiles/templates` 将当前 profile 另存为模板
- 存储位置：`model_profiles/.templates/{template_id}.json`，结构同 profile 但去掉 `checkpoint_path`
- `GET /api/profiles/templates` 返回内置 + 用户模板的合并列表，用户模板优先（同名覆盖内置）

## 5. API 设计

### 5.1 Profile CRUD

| 方法 | 路径 | 说明 |
|------|------|------|
| `GET` | `/api/profiles` | 列出所有 profile，返回简要信息列表 |
| `POST` | `/api/profiles` | 基于模板创建新 profile |
| `GET` | `/api/profiles/{id}` | 获取单个 profile 完整信息 |
| `PUT` | `/api/profiles/{id}` | 更新 profile（参数、路径、设备等） |
| `DELETE` | `/api/profiles/{id}` | 删除 profile 文件 |

### 5.2 模板

| 方法 | 路径 | 说明 |
|------|------|------|
| `GET` | `/api/profiles/templates` | 返回内置 + 用户自定义模板列表 |
| `POST` | `/api/profiles/templates` | 从指定 profile 创建用户模板 |

### 5.3 模型操作

| 方法 | 路径 | 说明 |
|------|------|------|
| `POST` | `/api/profiles/{id}/inspect` | 检查 checkpoint 文件完整性 |
| `POST` | `/api/profiles/{id}/load` | 加载模型到内存 |
| `POST` | `/api/profiles/{id}/unload` | 从内存卸载模型 |
| `POST` | `/api/profiles/{id}/test` | 快速测试（跑一帧推理验证可用性） |

### 5.4 回测（API 路由不变，参数调整）

| 方法 | 路径 | 说明 |
|------|------|------|
| `POST` | `/api/backtests/jobs` | 创建回测作业（`model_ids` → `profile_ids`） |
| `GET` | `/api/backtests/jobs/{job_id}` | 查询作业状态 |
| `GET` | `/api/backtests/runs` | 列出历史回测 |
| `GET` | `/api/backtests/runs/{run_id}` | 获取回测结果详情 |
| `GET` | `/api/backtests/runs/{run_id}/export` | 导出回测结果 |

**`POST /api/backtests/jobs` 请求体调整：**

```jsonc
{
  "profile_ids": ["act_pusht", "dp_push_t"],   // 改为 profile ID
  "episodes": [
    {"dataset_path": "/data/pusht", "episode_index": 0}
  ],
  "max_frames": null
}
```

### 5.5 环境信息

| 方法 | 路径 | 说明 |
|------|------|------|
| `GET` | `/api/models/env` | 保留不变，增加 `profiles_loaded` 字段 |

## 7. 实施计划

### Phase 1：核心系统（目标：一次配好反复用）

| 步骤 | 内容 | 产出 |
|------|------|------|

| **1f** | 迁移废弃 | 删除旧的 `MODEL_REGISTRY`、模型注册/加载 API，回测适配新 API |
| **1g** | 验证 | 完整端到端测试：创建 profile → 加载 → 回测 → 查看结果 |

| 步骤 | 内容 | 产出 |

| **2c** | 模板脚本 | `scripts/model_runner_template.py` — 用户复制改写的起点 |
| **2d** | Web 集成 | 创建 profile 时可选择 `custom_script` 适配器类型 |

## 8. Phase 2 预览：自定义脚本协议

### 8.1 协议设计

`custom_script` 适配器通过子进程 stdin/stdout 的 JSON 行协议与用户脚本通信：

```
Server (Python)                         Script process (用户语言)
     │                                         │
     │  subprocess.Popen(["python",             │
     │      "my_runner.py"])                    │
     │────────────────────────────────────────→│ 加载模型
     │                                         │ 输出: {"type":"ready"}
     │←────────────────────────────────────────│
     │                                         │
     │  {"type":"predict",                      │
     │   "observation":{...}}                   │
     │────────────────────────────────────────→│ policy.select_action(obs)
     │  {"type":"action",                       │
     │   "action":[0.12, 0.34]}                 │
     │←────────────────────────────────────────│
     │                                         │
     │  {"type":"reset"}                        │
     │────────────────────────────────────────→│ policy.reset()
     │  {"type":"ok"}                           │
     │←────────────────────────────────────────│
     │                                         │
     │  {"type":"close"}                        │
     │────────────────────────────────────────→│ 进程退出
```

### 8.2 用户脚本模板

```python
# model_runner.py — 用户按需修改
import sys, json
import torch
# ↑ 可以换成用户自己的环境、自己的依赖

# 1. 加载模型（用户自己写）
model = torch.load("my_model.pt")
model.eval()

print(json.dumps({"type": "ready"}), flush=True)

# 2. 推理循环
for line in sys.stdin:
    msg = json.loads(line)
    if msg["type"] == "predict":
        obs = msg["observation"]
        action = model.predict(obs)           # 用户自己的推理逻辑
        print(json.dumps({"type": "action", "action": action.tolist()}), flush=True)
    elif msg["type"] == "reset":
        model.reset()
        print(json.dumps({"type": "ok"}), flush=True)
    elif msg["type"] == "close":
        break
```

**关键规则：**
- 每个 JSON 消息独占一行（JSONL）
- 发送后必须 `flush`
- 超时 30 秒未响应视为异常
- 脚本的 venv 与项目完全隔离

## 9. 设计决策记录

| # | 决策 | 选项 A | 选项 B | 选择 | 理由 |
|---|------|--------|--------|------|------|
| 1 | 持久化格式 | SQLite 数据库 | 独立 JSON 文件 | **JSON 文件** | 可手改、可 git 管理、结构直观、零依赖 |
| 2 | 自定义模型接入方式 | 直接 import Python 模块 | 子进程 JSON 协议 | **子进程协议** | 隔离依赖、支持任意语言、进程崩溃不影响服务 |
| 3 | 旧 MODEL_REGISTRY 处理 | 保留兼容 | 直接废弃 | **直接废弃** | 减少维护负担，旧代码无保留价值 |
| 4 | 模板来源 | 仅内置 | 内置 + 用户自定义 | **内置 + 用户** | PT 用户可能需要为不同项目创建不同模板 |
| 5 | 多设备同模型 | profile 内嵌套 device 列表 | 复制 profile 改 device | **复制 profile** | 简单直观，避免结构复杂度 |
| 6 | 回测前模型加载 | 用户手动逐个加载 | 勾选后自动加载 | **自动加载** | 减少操作步骤，做到"一键回测" |
| 7 | extra_params 值类型 | 自由 JSON | string/number/bool/null | **string/number/bool/null** | 前端 UI 能自动匹配控件，复杂类型放 notes 字符串 |
| 8 | Phase 1 vs 2 优先级 | 先做自定义脚本 | 先做持久化复用 | **先做持久化** | 解决用户最高频痛点，Phase 2 在 Phase 1 稳定后推进 |

## 附录 B：适配器注册协议

```python
# app/adapters/__init__.py

ADAPTER_REGISTRY: dict[str, type[BacktestAdapter]] = {}

def register_adapter(name: str, cls: type[BacktestAdapter]) -> None:
    if name in ADAPTER_REGISTRY:
        raise ValueError(f"Adapter '{name}' already registered")
    ADAPTER_REGISTRY[name] = cls

def get_adapter(name: str) -> type[BacktestAdapter]:
    if name not in ADAPTER_REGISTRY:
        raise ValueError(f"Unknown adapter: {name}")
    return ADAPTER_REGISTRY[name]

def list_adapters() -> list[str]:
    return list(ADAPTER_REGISTRY.keys())
```
