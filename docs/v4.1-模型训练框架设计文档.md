# LeRobot Viewer v4.1 — 模型训练框架设计文档

> 本文档描述 v4.1 模型训练框架的设计。它建立在 v4.0 模型回测框架之上，沿用相同的架构模式。
> v4.0 的实际实现细节见 `docs/v4.0-模型回测设计文档.md`，本文档多处引用其现有接口。

## 0. 当前实现修订记录

按当前代码落地情况，v4.1 对原始方案做了几处工程化调整：

| 项目 | 原设计 | 当前实现 |
|---|---|---|
| 队列恢复 | 服务启动即自动恢复 queued 任务 | 不在模块 import 时启动训练；首次访问训练 API 或提交作业时启动 scheduler，并恢复 queued 任务 |
| 运行中作业恢复 | 检查 pid 后继续追踪 | 服务重启后无法重新绑定旧 stdout，旧 running 作业标记为 failed，避免误判 |
| 流水线 | 自动训练→回测→报告全流程 | 当前实现轻量流水线记录：创建流水线会提交训练作业并保存对比 profile / episode；训练完成后自动回测作为后续增强 |
| 自定义脚本 trainer | Phase 2 文件列入清单 | 当前未实现 `custom_script.py`，只保留扩展方向 |
| 真实训练测试 | 加载真实 LeRobot 训练环境 | 当前环境不具备真实训练条件，使用隐藏 `mock` trainer 完成端到端自测 |
| 自动 profile | 使用 recipe_id 作为 profile_id | 如果同名 profile 已存在，自动追加短后缀，避免覆盖已有 profile |

## 1. 背景与动机

### 1.1 现状与痛点

v4.0 已经建立了完善的模型档案（Model Profile）和回测系统，但训练环节缺失：

| # | 痛点 | 表现 |
|---|------|------|
| 1 | **训练命令与参数对不上** | 每次手动敲 `lerobot-train`，参数多、容易填错，事后记不清当时用了什么参数，checkpoint 和训练参数失去关联 |
| 2 | **半夜训练完不会自动跑下一个** | 一个训练任务凌晨 3 点结束，GPU 空闲到早上 9 点，浪费算力 |
| 3 | **想对比多组参数效果** | 换 batch_size、learning_rate、epochs 做消融实验，每次都要手动改命令，没有结构化记录 |
| 4 | **训练-回测-报告是断开的** | 训练完成 → 手动创建 Profile → 手动跑回测 → 手动对比结果，流程冗长 |

### 1.2 目标

1. **训练配置可管理**：所有训练参数持久化为结构化配方（Training Recipe），Web 上创建、编辑、复用
2. **自动队列执行**：提交训练到队列后，当前任务结束自动启动下一个，无需人工值守
3. **参数可调可对比**：内置 ACT / DP / VQ-BeT 训练模板，所有超参数可通过 Web 修改，支持自定义 key-value
4. **训练→回测自动桥接**：训练完成后自动生成 Model Profile，无缝衔接 v4.0 回测系统（**回测代码零改动**）
5. **框架可扩展**：先支持 `lerobot-train` CLI，后续可通过 TrainingFramework 适配器接入任意训练框架

### 1.3 约束

- 训练数据选择保持 lerobot 官方设定：**一个配方只对应一个数据集**（或数据集下的部分 episode）
- 回测 API 和 Profile 格式**完全不动**，桥接通过训练完成后写标准 Profile JSON 实现
- 训练和推理使用**子进程执行 CLI**，与主服务进程隔离依赖

## 2. 核心设计：Training Recipe

### 2.1 概念

对标 v4.0 的 Model Profile，Training Recipe 是一次训练任务的结构化配方，持久化为磁盘 JSON 文件。

```
Model Profile（v4.0）          Training Recipe（v4.1）
─────────────────────          ────────────────────────
模型的身份档案                 训练的配置配方
存于 state/model_profiles/    存于 state/training_recipes/
用于回测/推理                  用于训练执行
通过适配器加载模型              通过框架适配器执行训练
```

### 2.2 文件布局

```
state/
├── model_profiles/           ← v4.0 已有
│   ├── act_pusht.json
│   └── ...
├── training_recipes/         ← v4.1 新增
│   ├── act_bs128_lr1e4.json
│   ├── dp_horizon16.json
│   └── ...
├── training_jobs/            ← v4.1 新增
│   ├── job_001.json
│   ├── job_002.json
│   └── ...
└── backtests/                ← v4.0 已有，不改
```

- 配方文件名 = `{recipe_id}.json`，`recipe_id` 规则同 `profile_id`：`^[a-z0-9_-]+$`
- 作业文件名 = `{job_id}.json`，`job_id` 格式为 `job_` 前缀 + 序号

### 2.3 Recipe 数据结构

```jsonc
{
  // ── 基本元数据 ──
  "id": "act_bs128_lr1e4",
  "name": "ACT pusht bs=128 lr=1e-4",
  "description": "增大 batch size、降低 learning rate 的对比实验",

  // ── 训练框架 ──
  "framework": "lerobot_train",

  // ── 数据集选择（单数据集，可过滤 episode）──
  "dataset_path": "/data/datasets/pusht",
  "episode_filter": null,

  // ── 输出目录 ──
  "output_dir": "/data/checkpoints/act_bs128_lr1e4",

  // ── 训练超参数（模板提供默认值，Web 可改）──
  "hyperparams": {
    "policy_type": "act",
    "batch_size": 128,
    "epochs": 1000,
    "learning_rate": 0.0001,
    "weight_decay": 0.0,
    "lr_scheduler": "cosine",
    "n_obs_steps": 2,
    "n_action_steps": 8,
    "chunk_size": 100,
    "temporal_agg": true,
    "num_workers": 4
  },

  // ── 硬件配置 ──
  "device": "cuda",
  "launcher": "accelerate",
  "gpu_devices": "0,1",
  "num_processes": 2,
  "env_vars": {
    "NCCL_DEBUG": "WARN"
  },

  // ── 用户自定义扩展参数 ──
  "extra_params": {
    "experiment_group": "learning_rate_sweep",
    "notes": "lr 从 1e-3 降到 1e-4，观察收敛速度差异"
  },

  // ── 训练→回测桥接 ──
  "auto_profile_on_complete": true,
  "profile_name": "ACT bs128 lr1e-4",
  "profile_adapter": "lerobot_official",

  // ── 时间戳 ──
  "created_at": "2026-06-02 10:00:00",
  "updated_at": "2026-06-02 14:30:00"
}
```

**字段说明：**

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `id` | string | ✓ | 唯一标识，文件名，只允许 `[a-z0-9_-]+` |
| `name` | string | ✓ | 显示名称 |
| `description` | string | | 自由描述 |
| `framework` | string | ✓ | 训练框架名称，如 `lerobot_train` |
| `dataset_path` | string | ✓ | 数据集根目录路径 |
| `episode_filter` | array \| null | | `null` = 全部 episode；`[0,5,10]` = 仅选这些 episode |
| `output_dir` | string | ✓ | 训练输出目录（checkpoint 保存位置） |
| `hyperparams` | object | ✓ | 训练超参数，每个框架定义自己的默认键 |
| `device` | string | ✓ | 设备名，如 `cuda`、`cuda:0`、`cpu` |
| `launcher` | string | | 启动方式：`direct` 或 `accelerate` |
| `gpu_devices` | string | | 写入训练子进程 `CUDA_VISIBLE_DEVICES`，如 `0`、`0,1` |
| `num_processes` | integer | | `accelerate launch --num_processes`，单卡为 1，双卡通常为 2 |
| `env_vars` | object | | 训练子进程环境变量，值会转成字符串 |
| `extra_params` | object | | 用户自定义扩展参数 |
| `auto_profile_on_complete` | boolean | | 训练完成后是否自动生成 Model Profile（默认 true） |
| `profile_name` | string | | 自动生成的 profile 显示名称 |
| `profile_adapter` | string | | 自动生成的 profile 适配器 |

**与 Model Profile 的对应关系：**

```
Recipe                        → 训练完成后自动生成 →  Profile
─────────────────────────────────────────────────────────────
output_dir                    → checkpoint_path
profile_name                  → name
profile_adapter               → adapter
device                        → device
hyperparams（推理相关部分）     → runtime_params
extra_params（部分透传）       → extra_params
```

### 2.4 超参数编辑规范

沿用 v4.0 profile 的参数表格模式：

- `hyperparams`：框架定义默认键，用户可编辑值、可增加新键，**不可删除框架必需的键**
- `extra_params`：用户自由增删改
- 值类型：`string`、`number`、`boolean`、`null`、`json`
- 前端根据值类型自动选择控件（文本框 / 数字输入 / 开关 / JSON 编辑器）

### 3.2 TrainingFramework 基类

```python
# app/trainers/__init__.py

class TrainingFramework(ABC):
    """训练框架适配器基类。与 BacktestAdapter 模式一致。"""

    framework_name: str          # 注册时使用的名称
    label: str                  # UI 展示名称
    visible_in_ui: bool = True
    test_only: bool = False

    @classmethod
    def default_hyperparams(cls) -> dict[str, Any]:
        """返回该框架的默认超参数模板。"""
        return {}

    @classmethod
    def validate_recipe(cls, recipe: dict[str, Any]) -> list[str]:
        """校验配方完整性，返回错误列表。"""
        return []

    @abstractmethod
    def build_command(self, recipe: dict[str, Any]) -> list[str]:
        """根据配方构建实际执行的 CLI 命令。"""
        ...

    @abstractmethod
    def parse_progress(self, line: str) -> dict[str, Any] | None:
        """从 stdout/stderr 的一行文本中解析训练进度。
        返回 None 表示这行不是进度信息。
        返回 dict 包含 epoch/step/loss/lr 等进度字段。"""
        ...

    def estimate_output_dir(self, recipe: dict[str, Any]) -> str:
        """推断训练输出目录。默认直接返回 recipe 的 output_dir。"""
        return recipe.get("output_dir", "")

    def inspect_recipe(self, recipe: dict[str, Any]) -> dict[str, Any]:
        """训练前检查：数据集是否存在、输出目录是否可写、CLI 是否可用等。"""
        return {"valid": True, "errors": [], "warnings": []}
```

### 3.3 lerobot_train 适配器

```python
# app/trainers/lerobot_train.py

class LeRobotTrainer(TrainingFramework):
    framework_name = "lerobot_train"
    label = "LeRobot Train (CLI)"

    @classmethod
    def default_hyperparams(cls) -> dict[str, Any]:
        return {
            "policy_type": "act",
            "batch_size": 64,
            "epochs": 1000,
            "learning_rate": 0.0001,
            "weight_decay": 0.0,
            "lr_scheduler": "cosine",
            "n_obs_steps": 2,
            "n_action_steps": 8,
            "chunk_size": 100,
            "temporal_agg": True,
        }

    def build_command(self, recipe: dict[str, Any]) -> list[str]:
        hp = recipe.get("hyperparams", {})
        command = [
            "lerobot-train",
            f"policy={hp.get('policy_type', 'act')}",
            f"dataset_path={recipe['dataset_path']}",
            f"output_dir={recipe['output_dir']}",
            f"batch_size={hp.get('batch_size', 64)}",
            f"epochs={hp.get('epochs', 1000)}",
            f"learning_rate={hp.get('learning_rate', 1e-4)}",
            f"device={recipe.get('device', 'cuda')}",
            # ... 更多参数映射
        ]
        if recipe.get("launcher") == "accelerate":
            prefix = [
                "accelerate",
                "launch",
                "--num_processes",
                str(recipe.get("num_processes", 1)),
            ]
            if int(recipe.get("num_processes", 1)) > 1:
                prefix.append("--multi_gpu")
            return prefix + command
        return command

    def parse_progress(self, line: str) -> dict | None:
        # 解析 lerobot-train 的典型输出：
        # "Epoch 342/1000 | loss: 0.0234 | lr: 8.5e-05"
        import re
        m = re.match(
            r"Epoch\s+(\d+)/(\d+)\s*\|\s*loss:\s*([\d.]+)\s*\|\s*lr:\s*([\de.+-]+)",
            line
        )
        if m:
            return {
                "epoch": int(m.group(1)),
                "total_epochs": int(m.group(2)),
                "loss": float(m.group(3)),
                "lr": float(m.group(4)),
            }
        return None
```

## 5. 训练作业队列

### 5.1 设计目标

这是解决"半夜训练完不会自动跑下一个"的核心模块。

- 提交作业 → 进入队列（持久化到磁盘）
- 当前作业完成 → 自动从队列取出下一个执行
- 服务重启 → 队列自动恢复
- 用户可拖拽排序、取消、重新排队

### 5.2 与 v4.0 回测队列的差异

| 特性 | v4.0 回测队列 | v4.1 训练队列 |
|------|-------------|-------------|
| 存储 | 进程内 `BACKTEST_JOBS` 字典 | 磁盘 `state/training_jobs/*.json` |
| 执行器 | `ThreadPoolExecutor(max_workers=1)` | 独立子进程（`subprocess.Popen`） |
| 服务重启 | 队列丢失 | 队列恢复 |
| 作业数量 | 一般 1-2 个 | 可能排队 10+ 个 |
| 实时日志 | 不采集（回测结果一次性返回） | 采集 stdout/stderr 日志流 |
| 进度解析 | 无（回测一次性完成） | 实时解析，前端轮询显示 |

### 5.3 Job 数据结构

```jsonc
{
  "job_id": "job_003",
  "recipe_id": "act_bs128_lr1e4",
  "recipe_snapshot": { /* 提交时 recipe 的完整快照 */ },
  "status": "running",
  "pid": 12345,
  "queue_position": 0,
  "created_at": "2026-06-02 22:00:00",
  "started_at": "2026-06-02 23:30:00",
  "finished_at": null,
  "progress": {
    "epoch": 342,
    "total_epochs": 1000,
    "step": null,
    "total_steps": null,
    "loss": 0.0234,
    "lr": 0.000085,
    "elapsed_seconds": 4523.0,
    "last_update": "2026-06-03 00:45:23"
  },
  "log_file": "state/training_jobs/job_003.log",
  "error": null,
  "auto_generated_profile_id": null
}
```

**字段说明：**

| 字段 | 说明 |
|------|------|
| `job_id` | 唯一作业 ID |
| `recipe_id` | 关联的配方 ID |
| `recipe_snapshot` | 提交时的配方完整快照（防止配方后续被修改影响追溯） |
| `status` | `queued` → `running` → `done` \| `failed` \| `cancelled` |
| `pid` | 运行中的子进程 PID |
| `queue_position` | 队列位置（运行时为 0，排队时 ≥ 1） |
| `progress` | 实时训练进度，由适配器的 `parse_progress()` 更新 |
| `log_file` | stdout/stderr 日志文件路径 |
| `auto_generated_profile_id` | 训练完成时自动生成的 Model Profile ID |

```
              POST /api/train/jobs
                    │
                    ↓
                ┌────────┐     队列轮到此作业        ┌─────────┐
                │ queued │ ───────────────────────→ │ running │

              ┌──────────┐                      ┌──────┐ ┌────────┐
```

### 5.5 队列调度器

```python
# app/training_executor.py — 核心调度逻辑

class TrainingScheduler:
    """单 worker 训练调度器。"""

    def __init__(self):
        self._current_process: subprocess.Popen | None = None
        self._current_job_id: str | None = None
        self._log_thread: threading.Thread | None = None
        self._lock = threading.Lock()

    def submit(self, job_id: str) -> None:
        """提交作业到队列尾部。如果当前没有运行中的作业，立即启动。"""

    def cancel(self, job_id: str) -> None:
        """取消排队中的作业，或终止运行中的作业。"""

    def _on_job_done(self, job: dict) -> None:
        """作业完成回调：
        1. 如果 recipe 开了 auto_profile_on_complete，自动生成 Model Profile
        2. 从 queue 取下一个作业启动
        """

    def _stream_logs(self, process, job_id) -> None:
        """后台线程：读取子进程 stdout/stderr，写入日志文件，
        调用 trainer.parse_progress() 更新进度。"""
```

**调度行为规则：**
- 同一时刻只运行一个训练作业（避免 GPU OOM）
- 上一个作业结束后，立即从队列取下一个
- 服务重启时：检查 `running` 状态的作业 → 进程已不存在则标记 `failed`，然后从 `queued` 列表取第一个启动
- 如果未来有多 GPU，可扩展为每 GPU 一个并发槽

### 5.6 持久化保证

训练作业队列完全落盘：

```
state/training_jobs/
├── job_001.json     ← 已完成，status: done
├── job_002.json     ← 已完成，status: failed
├── job_003.json     ← 运行中，status: running，含 pid
├── job_004.json     ← 排队中，status: queued
├── job_005.json     ← 排队中，status: queued
├── job_001.log      ← job_001 的训练日志
├── job_002.log
├── job_003.log
├── job_004.log      ← 排队中的作业无日志（未开始）
└── job_005.log
```

对比 v4.0 回测队列：回测作业是进程内字典，服务重启丢失队列（已完成的结果存在 `state/backtests/` 中不受影响）。训练作业因为可能要排队数小时，**必须**磁盘持久化。

## 6. 与 v4.0 回测的桥接

### 6.1 核心原则

> **回测代码一行不改。** 桥接完全通过文件系统和已有 API 实现。

### 6.2 训练完成 → 自动生成 Profile

训练作业 `done` 时，调度器检查 recipe 的 `auto_profile_on_complete`：

```python
def _auto_create_profile(job: dict) -> str | None:
    recipe = job["recipe_snapshot"]
    if not recipe.get("auto_profile_on_complete"):
        return None

    profile_id = recipe["id"]  # 用 recipe_id 作为 profile_id
    profile_data = {
        "id": profile_id,
        "name": recipe.get("profile_name") or recipe["name"],
        "description": f"自动生成自训练配方 {recipe['id']}（作业 {job['job_id']}）",
        "checkpoint_path": recipe["output_dir"],
        "adapter": recipe.get("profile_adapter") or recipe["framework"],
        "device": recipe.get("device", "cuda"),
        "runtime_params": _extract_inference_params(recipe),
        "extra_params": dict(recipe.get("extra_params", {}),
                             _auto_generated_from=recipe["id"],
                             _auto_generated_job=job["job_id"]),
    }
    # 调用 profile_store.create_profile() → 写 JSON 到 state/model_profiles/
    # 调用 profile_store 的 inspect 检查 checkpoint 完整性
    # 返回 profile_id
```

**`_extract_inference_params()` 的转换逻辑：**

将 recipe 的 `hyperparams` 中与推理相关的键提取到 profile 的 `runtime_params`：

```python
# recipe hyperparams 中这些键直接拷贝到 profile runtime_params
INFERENCE_KEYS = {
    "policy_type", "temporal_agg", "n_obs_steps", "n_action_steps",
    "chunk_size", "horizon", "num_inference_steps",
}

def _extract_inference_params(recipe: dict) -> dict:
    return {
        k: v for k, v in recipe["hyperparams"].items()
        if k in INFERENCE_KEYS
    }
```

生成的 Profile 与用户手动创建的 Profile **完全一致**——文件结构和字段语义无任何区别。回测系统无法区分它是否来自自动生成。

### 6.3 数据流图

```
Training Recipe ──submit──→ Training Job Queue

                            │               │
```

### 6.4 训练→回测→报告流水线

流水线是一个独立的编排模块 `app/training_pipeline.py`，不修改训练和回测的内部逻辑：

```python
class TrainingPipeline:
    """编排 训练 → 回测 → 报告 的流水线。"""

    pipeline_id: str
    recipe_id: str
    comparison_profile_ids: list[str]
    episodes: list[dict]
    max_frames: int | None
    status: str   # waiting → training → backtesting → done | failed

    async def execute(self):
        # Step 1: 提交训练作业
        job = submit_training_job(self.recipe_id)
        # 轮询等待作业完成
        while job["status"] == "running":
            await sleep(30)
            job = get_training_job(job["job_id"])

        # Step 2: profile 已由调度器自动创建（或调用 API 手动创建）

        # Step 3: 提交回测
        backtest_job = await api_post("/api/backtests/jobs", {
            "profile_ids": [job["auto_generated_profile_id"]] + self.comparison_profile_ids,
            "episodes": self.episodes,
            "max_frames": self.max_frames,
        })
        # 轮询等待回测完成
        while backtest_job["status"] not in ("done", "failed"):
            await sleep(5)
            backtest_job = await api_get(f"/api/backtests/jobs/{backtest_job['job_id']}")

        # Step 4: 收集结果 → 生成对比报告
```

**关键点**：流水线通过 HTTP 调用已有 API 端点，不对回测系统做任何内部修改。

## 10. 设计决策记录

| # | 决策 | 选项 A | 选项 B | 选择 | 理由 |
|---|------|--------|--------|------|------|
| 1 | 训练 Recipe 存储 | 复用 profile JSON 结构 | 独立 Recipe JSON 结构 | **独立 Recipe** | 两者字段差异大（recipe 有 hyperparams 无 runtime_params，profile 反之），强行复用会让两个概念都变模糊 |
| 2 | 训练框架执行方式 | 直接 import 训练库 | 子进程执行 CLI | **子进程 CLI** | lerobot-train 是独立 CLI；子进程隔离依赖、crash 不影响服务；与 v4.0 custom_script 思路一致 |
| 3 | 训练队列持久化 | 进程内存（同回测队列） | 磁盘 JSON 文件 | **磁盘文件** | 训练作业可能排队数小时，服务重启不能丢失；回测队列是短任务可以不持久化，训练队列必须持久 |
| 4 | 回测桥接方式 | 在回测代码中插入钩子 | 训练完成写标准 Profile JSON | **写 Profile JSON** | v4.0 回测已经稳定，不改任何代码；Profile 文件系统是天然的 API 边界 |
| 5 | 流水线实现 | HTTP 调用已有 API | 内部函数调用 | **HTTP 调用 API** | 解耦；流水线失败不影响训练/回测系统；未来可迁移到独立进程 |
| 6 | 数据集选择 | 支持多数据集混合训练 | 保持 lerobot 单数据集设定 | **单数据集** | 按用户需求保留限制，降低实现复杂度 |
| 7 | 超参数与推理参数的边界 | 训练 recipe 包含推理需要的参数 | recipe 和 profile 参数完全独立 | **recipe 包含推理参数** | 训练的超参数（n_obs_steps、chunk_size 等）决定了推理行为，训练完成后自动提取到 profile runtime_params；避免用户填两次 |
| 8 | 训练作业日志存储 | 数据库 | 文本文件 | **文本文件** | 与 profile/backtest 的简约风格一致；`tail -f` 可直接看；前端通过 API 获取最近 N 行 |

## 附录 B：recipe → profile 自动转换规则

训练作业 `done` 时，调度器调用以下转换逻辑自动生成 Model Profile：

```python
def recipe_to_profile(recipe: dict, job_id: str) -> dict:
    """将 TrainingRecipe 转换为 ModelProfile 创建参数。"""
    hp = recipe.get("hyperparams", {})

    # 从 hyperparams 中提取推理相关键
    inference_keys = {
        "policy_type", "temporal_agg", "n_obs_steps", "n_action_steps",
        "chunk_size", "horizon", "num_inference_steps",
    }
    runtime_params = {k: v for k, v in hp.items() if k in inference_keys}

    # extra_params 加上溯源标记
    extra = dict(recipe.get("extra_params", {}))
    extra["_auto_generated_from_recipe"] = recipe["id"]
    extra["_auto_generated_from_job"] = job_id

    return {
        "id": recipe["id"],
        "name": recipe.get("profile_name") or recipe["name"],
        "description": f"自动生成自训练配方 {recipe['id']}（作业 {job_id}）",
        "checkpoint_path": recipe["output_dir"],
        "adapter": recipe.get("profile_adapter") or "lerobot_official",
        "device": recipe.get("device", "cuda"),
        "runtime_params": runtime_params,
        "extra_params": extra,
    }
```
